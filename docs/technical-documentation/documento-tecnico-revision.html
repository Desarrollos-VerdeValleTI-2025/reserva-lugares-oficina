1. Descripción del Sistema

1.1 Descripción general

¿Qué es? Una aplicación web interna de Verde Valle que permite a los empleados reservar un lugar/asiento físico de trabajo en la oficina para una fecha específica. Proporcionado por usuario

¿Para qué sirve / qué problema resuelve? Evita conflictos de asignación de espacios físicos de oficina y da visibilidad de disponibilidad por fecha. Proporcionado por usuario

¿Cómo encaja en el ecosistema tecnológico? Es un proyecto autocontenido (front + API + base de datos propios) que se integra únicamente con Microsoft Entra ID (Azure AD) para autenticación corporativa; no se integra con otros sistemas internos de Verde Valle (ERP, RH, etc.). Los README del propio repositorio indican explícitamente que es un proyecto simulado para capacitación, sin conexión con sistemas de producción reales. Validado por código

¿Qué tipo de solución es? Aplicación web de 3 capas: SPA (React) + API REST interna (Node/Express) + base de datos relacional propia (MySQL). No es un job, ni un servicio de integración, ni microservicios. Validado por código

¿Quiénes son los usuarios principales? Empleados de Verde Valle que necesitan reservar un lugar de trabajo en la oficina, autenticados con su cuenta corporativa. No existen roles diferenciados (ver sección 6). Proporcionado por usuario Validado por código

2. Arquitectura

2.1 Estilo Arquitectónico

Arquitectura cliente-servidor de 3 capas: SPA (frontend) → API REST interna (backend) → base de datos relacional propia (MySQL), accedida exclusivamente vía stored procedures. No es un monolito de proceso único (front y backend son despliegues independientes), no es microservicios (un solo servicio backend), no es event-driven (sin colas/brokers), y no hay evidencia de jobs/workers. La autenticación sigue el patrón "SPA + API protegida por OAuth2/OIDC", con audiencias separadas para front y backend (dos App Registrations de Azure AD). Validado por código

B. Flujo funcional principal

Empleado inicia sesión (Azure AD)
   → Front consulta "mis reservas" (GET /api/reservations/me)
      → ¿Tiene reserva activa?
          Sí → tarjeta (lugar, fecha) con opciones: Ver / Editar / Cancelar
          No → botón "Apartar lugar"
   → Empleado elige fecha
      → Front consulta disponibilidad (GET /api/seats?date=)
      → Empleado selecciona un lugar disponible
      → Front confirma (POST /api/reservations  ó  PUT /api/reservations/:id)
   → API valida (Azure AD + reglas de negocio en stored procedures)
   → MySQL valida disponibilidad/fecha/pertenencia, inserta o actualiza
   → API responde {success:true, data:{...}}
   → Front regresa a "Mis reservas" actualizado

4.3 Reglas de Integridad

  • PK autoincremental en ambas tablas; FK dbo_reservations.id_seat → dbo_seats.id.
  • dbo_seats.code es UNIQUE. No existe UNIQUE(id_seat, reservation_date) — decisión explícita para permitir re-reservar tras cancelación lógica.
  • Índices: idx_dbo_reservations_id_seat_reservation_date, idx_dbo_reservations_user_email.
  • Validaciones de negocio en SPs: parámetros no nulos, fecha no pasada, disponibilidad del lugar, pertenencia de la reserva al usuario (vía SIGNAL SQLSTATE '45000').
Resuelto — diseño confirmado, no era una contradicción

El script versionado 01_create_database.sql otorga SELECT, INSERT, UPDATE, EXECUTE directo al usuario de aplicación, a diferencia del README de la base de datos, que documenta un usuario con solo permiso EXECUTE vía rol dedicado. El desarrollador aclaró que estos permisos amplios fueron intencionales, para crear el usuario de aplicación dentro de la base de datos durante el despliegue; ya se ejecutó así en el entorno real.

Nota menor (fuera del alcance de este agente): el README de la base de datos podría actualizarse para reflejar esta realidad, pero no bloquea la operación del sistema.

6. Seguridad

6.1 Autenticación y Autorización

Mecanismo: OAuth2/OIDC vía Microsoft Entra ID (Azure AD) — MSAL en frontend, verificación manual de JWT (RS256) con jsonwebtoken + jwks-rsa en backend. Validado por código

Autorización: no hay autorización granular por rol — cualquier token válido del tenant configurado tiene acceso a todas las operaciones. La única verificación de "propiedad" es a nivel de dato: los SPs de editar/cancelar validan que user_email coincida con el del token.
